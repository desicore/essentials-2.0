# Q4 — Resource conflicts (room, facilitator, equipment) surfaced at creation

**7shifts** (`mobbin:8796902e-18e6-4f82-98d8-2146b96be325`): pre-publish "We found some warnings" modal counts Exceptions/Conflicts/Overtime/Unassigned Shifts and offers "Yes, fix them for me" or "No thanks" — a **soft, batch** gate shown at *publish*, not at single-shift creation, and it's a scheduling-conflict tally, not per-resource detail.

**Acuity Scheduling** (`refero:9868`, flow, 5 images): opening/editing an existing class shows a yellow banner "This class conflicts, there is another event blocking off this time" naming the resource ("this uses resource Room #5") but explicitly still lets the class run ("will still be available to clients") and saves successfully. This is a clear **soft/warn-only, room-conflict, edit-time** case — not creation, not blocking.

**Clockwise** (`mobbin:671e0870…`): "I can schedule this meeting, but there is a conflict for Sam" plus "Sam has conflicts that I can't fix" — **person/attendee** conflict, soft warning with Confirm still available, shown while scheduling (ambiguous whether first creation or adjustment).

**Fresha** (`mobbin:ac5e971e…`): editing a service booking shows "Alex Smith is not working between 7:00am and 7:45am" — **facilitator/staff-availability** conflict, soft (Apply still enabled), on an edit screen.

**Google Workspace** (`mobbin:0a1650e1…`): "Add resource" dialog lists rooms/equipment with capacity — proves a room/equipment *picker* exists, not that conflict checking happens; no warning visible.

**Reclaim AI** (`refero:4117`, flow): marketing screen only; the actual "Smart Meeting" edit form shown has no visible attendee-availability indicator in these frames — take's claim of inline calendar status is **not evidenced** by the captured images.

**SavvyCal** (`mobbin:44fd56e6…`): "Override availability" modal with "Ignore calendar conflicts" toggle — implies conflict detection exists elsewhere, but this screen is a manual bypass control, not the conflict surfacing itself.

**Zoom** (`mobbin:2ef394f0…`): "You are already in another meeting" — person conflict, but at *start time*, not creation.

**Understory** (`refero:12709` + counter-example `refero:023aed7b`): resources are modeled with quantity (`12709`), and the creation modal (`023aed7b`) shows a "Resources: 1 rule" field but **no conflict warning anywhere in the create flow** — good counter-example that a resource field alone doesn't demonstrate conflict detection at creation.

## Distinctive pattern
Every real conflict message found is **soft (warn, don't block)** and appears on **edit/reopen or pre-publish**, never inside the initial creation form. None show a hard block.

## Counter-example
`refero:023aed7b-e219-4ddc-8374-63091cfda3f7` (Understory creation modal, marked `counter_example: true`) — resource field present, zero conflict UI at creation.

## Evidence gaps
No product shows conflict detection live *while filling the creation form*; all captured warnings are post-save (edit/reopen) or pre-publish batch. Equipment-specific conflicts (vs. room/person) are not evidenced anywhere.
