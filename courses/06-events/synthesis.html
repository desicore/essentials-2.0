Synthesis

Read this first. Sections Q1–Q6 below hold the evidence cards; every product and reference id named here is in the report. Ids are shortened to their first block (for example refero:12719, mobbin:1680974d).

Top examples

  1. Understory (Refero, refero:12719) — "+ Event" starts by picking an existing Experience, and the session form arrives pre-filled with capacity, location, rooms and guides. The closest thing to "schedule a scenario" in the whole set.
  2. Kajabi (Mobbin, mobbin:1680974d, mobbin:c497ddd0) — sessions scheduled inline under a coaching product, with a separate global Events calendar that has no product link (mobbin:64f56885). Shows both surfaces in one product.
  3. Luma (Refero, refero:1848) — turns a single event into a multi-session series: cadence, number of weeks, weekday chips, or a hand-written session list. The best model for a course whose sessions do not repeat identically.
  4. Acuity Scheduling (Refero, refero:9868) — reopening a class shows "this class conflicts … uses resource Room #5" and still lets it save. The only explicit room-conflict message found.
  5. Lyssna (Mobbin, mobbin:8a3407fe) — host marks a session Completed or No-show, with automatic completion after five days. Attendance with a fallback.
  6. Partiful (Refero, refero:10204) — RSVP with a plus-one where the spot counter decrements per person (20/20 → 18/20). The most literal seat accounting.
  7. Microsoft Teams (Refero, refero:9746) — from an empty events state through the whole create form: time zone first, start/end with computed duration, all-day toggle.
  8. Amie / Motion (Mobbin, mobbin:1c7e609d, mobbin:1eb73c81) — the two-option "this event / all events" dialog, the only edit-scope pattern in the set.

What the best apps do differently

  1. They start the event from the thing that runs, not from a blank date. Understory picks the Experience first and pre-fills the form (refero:12719); Workable opens the event from the candidate record (mobbin:da2ca788); Acuity defines the class type once and offers instances later (refero:9859). Everyone else starts with a title field.
  2. They keep inline and global surfaces both, but only one of them knows the course. Kajabi's product sessions are inline (mobbin:1680974d) while its Events calendar is a marketing tool with no product link (mobbin:64f56885); Luma's calendar picker applies the tag at creation (refero:1843). Circle shows the failure mode: course spaces exist but the event form lives under a global tab (mobbin:b360aa69).
  3. They treat a series as a list of sessions, not a rule. Luma builds the series from an existing event and lets you either generate by cadence or write the sessions out (refero:1848). Rule-only products (Zoom mobbin:b85c076b, Understory refero:12705) give no way to see or edit the resulting dates.
  4. Conflicts are warnings, and they arrive late. Acuity (refero:9868), Fresha (mobbin:ac5e971e) and Clockwise (mobbin:671e0870) all warn and still allow save; 7shifts batches the check at publish (mobbin:8796902e). Nobody shows live per-resource availability inside the form, and nobody covers equipment.
  5. Attendance has a fallback. Lyssna auto-completes unmarked sessions after five days (mobbin:8a3407fe), Posh gives the host a one-tap check-in (mobbin:4022cce6). Capacity products (Understory refero:12706, Eventbrite mobbin:c0b0ead0) never show what happens when it is full: no waitlist in the set.
  6. Time zone is a first-class field, duration is a preset. Teams puts the zone above the dates (refero:9746); Kajabi, SavvyCal and Clockwise pair a zone dropdown with duration chips (mobbin:5de887fe, mobbin:9a8fc4f4, mobbin:1fe20459). Homerun's start-plus-duration with a read-only zone label (refero:7186) is the simpler fit for a single physical site.

Best practices top companies converge on

  • Create the event inside the course; mirror it into the global calendar as a filtered view with the course as tag. Never a second, unlinked calendar.
  • Open the form from the scenario (or from the group): pre-fill title, duration, rooms and equipment from the scenario definition.
  • Attendees are an object (a learner group), not a list of names; individuals are added on top.
  • Offer a repeat rule for convenience, but always render the resulting session list so dates can be edited one by one; when a series edit happens, ask "this session / all sessions".
  • Warn on room, facilitator and equipment conflicts; do not block. Show the warning while the form is open, not after save.
  • Capacity is a number with a "no limit" option; attendance is marked by the facilitator with an automatic resolution after a grace period.
  • One institutional time zone shown as a label; duration defaults from the scenario and is editable as presets.

Open questions for Essentials 2.0

  • Session ≠ recurrence. A course typically runs the same scenario for several groups in rotation, and different scenarios on the same day. Is the unit "one event with several slots" (Luma's session list) or "one event per group per slot"? This decides how modules 04 and 05 hang off the event.
  • Where does the link show from the other side? No reference shows a content or group page listing its events. The scenario page (05) and the learner group page (04) both need a "Sessions" section that this module has to specify.
  • Resource model before conflict UI. Rooms, manikins and facilitators need to be bookable objects with quantities (Understory's model) before any warning can be drawn. Is that owned by the course module or by an institution-level settings area?
  • Assigned vs. sign-up. All the sign-up patterns here are self-service. If groups are attached, sign-up is unnecessary; if slots are open, a waitlist is needed and no reference shows one. Which of the two does the Learner Portal (07) expose?
  • Canvas and calendar hand-off. Once events exist, module 10 has to push them to learners and to Canvas. Which fields are source of truth here (room, facilitator, capacity) and which can be edited on the Canvas side?
